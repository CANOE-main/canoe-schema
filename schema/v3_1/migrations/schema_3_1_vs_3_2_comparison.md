# Schema Comparison: 3.1 vs 3.2

## 1. New "Label" Tables in 3.2

The biggest architectural change is the introduction of three new lookup/label tables that act as global registries decoupled from `data_id`:

- **`TechnologyLabel`** (`tech TEXT PRIMARY KEY, notes TEXT`) — a global list of all technology names.
- **`CommodityLabel`** (`commodity TEXT PRIMARY KEY, notes TEXT`) — a global list of all commodity names.
- **`DataSourceLabel`** (`source_id TEXT PRIMARY KEY, notes TEXT`) — a global list of all data source IDs.

These don't exist at all in 3.1.

---

## 2. Foreign Key Pattern: Global Labels vs. Scoped References

This is the pervasive change that affects nearly every table. In 3.1, foreign keys for tech, commodity, and data source always include `data_id` in the reference, scoping them to a specific dataset:

```sql
-- 3.1 pattern
FOREIGN KEY (tech, data_id) REFERENCES Technology (tech, data_id)
FOREIGN KEY (data_source, data_id) REFERENCES DataSource (source_id, data_id)
FOREIGN KEY (input_comm, data_id) REFERENCES Commodity (name, data_id)
```

In 3.2, these are replaced with references to the new global label tables, dropping the `data_id` scope entirely:

```sql
-- 3.2 pattern
FOREIGN KEY (tech) REFERENCES TechnologyLabel (tech)
FOREIGN KEY (data_source) REFERENCES DataSourceLabel (source_id)
FOREIGN KEY (input_comm) REFERENCES CommodityLabel (commodity)
```

This affects every table that references tech, commodity, or data source — essentially the entire schema.

## 3. `Technology` Table

3.2 adds a new foreign key:
```sql
FOREIGN KEY (tech) REFERENCES TechnologyLabel (tech)
```
3.1 has no such self-referencing global constraint on `tech`.

## 4. `DataSource` Table

3.2 adds:
```sql
FOREIGN KEY (source_id) REFERENCES DataSourceLabel (source_id)
```
3.1 has no such constraint; `DataSource` was itself the root reference for source IDs.

## 5. `LimitAnnualCapacityFactor` — Schema Change (Column Added)

3.1:
```sql
region, period, tech, output_comm, operator, factor, ...
PRIMARY KEY (region, period, tech, output_comm, operator, data_id)
```

3.2 adds a **`vintage`** column and removes **`period`**:
```sql
region, tech, vintage INTEGER REFERENCES TimePeriod(period), output_comm, operator, factor, ...
PRIMARY KEY (region, tech, vintage, output_comm, operator, data_id)
```

This table's scope changes from period-based to vintage-based.

## 6. `LinkedTech` — Foreign Key Change

Same pattern as the global label migration. `LinkedTech` still retains the `data_id`-scoped FKs for `primary_tech` and `driven_tech` (referencing `Technology`), since `Technology` itself is still dataset-scoped.

## 8. `TimePeriod` — Pre-populated Data in 3.2

3.1's `TimePeriod` is defined with no seed rows.

## 9. Duplicate `SeasonLabel` Definition in 3.2 (likely a bug)

3.2 defines `SeasonLabel` **twice**. The first definition (at the top, same as 3.1):
```sql
CREATE TABLE IF NOT EXISTS SeasonLabel (season TEXT PRIMARY KEY, notes TEXT);
```
Then a second definition appears near the bottom with a **different column name**:
```sql
CREATE TABLE IF NOT EXISTS SeasonLabel (tech TEXT PRIMARY KEY, notes TEXT);
```
The second one uses `tech` as the primary key column instead of `season`. Because of `CREATE TABLE IF NOT EXISTS`, the second statement will be silently ignored at runtime, but this looks like a copy-paste error in 3.2.
